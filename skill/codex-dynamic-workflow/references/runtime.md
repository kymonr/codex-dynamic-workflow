# v4 Runtime protocol

## Entry and authority
This package bundles `../scripts/cwf.py` relative to this reference directory (the Skill-root path is `scripts/cwf.py`). Python 3.11+ standard library only. From the source project use `python -B scripts/workflow.py`; from an installed Skill use `python -B <skill-dir>/scripts/cwf.py`. Append `--db <explicit-local-database>` before a subcommand. `--version` and `--help` need no initialized database.
Ordinary Skill-only native use stays available. Runtime is selected explicitly for persistence/control: one local DB coordinates admissions and cooperative locks. Current model delegation is native-only for both Luna and Astra; the Python controller manages state while Root uses actual native host tools to execute. Root retains authorization and proposes tasks; Runtime alone admits and charges each managed run. Do not dispatch its nodes outside returned packets or reset task limits with new run IDs. Historical exec contracts retain their recorded identity and accounting.
The database is trusted local controller state, not a multi-tenant security boundary. A malicious process with DB write access can defeat it. Child results are untrusted data; only the authorized Root/host may issue create/add/refresh/resume/decide/release commands. Model output cannot authorize any of these actions. Use host sandbox/approval controls in addition to runtime checks.

## Minimal command flow
```text
python -B scripts/workflow.py --db .delivery/runtime.sqlite init
python -B scripts/workflow.py --db .delivery/runtime.sqlite create --plan examples/runtime-readonly.json
python -B scripts/workflow.py --db .delivery/runtime.sqlite status --run RUN_ID
python -B scripts/workflow.py --db .delivery/runtime.sqlite next --run RUN_ID --backend native
```
Use the returned run ID and attempt token, not the placeholders above. The example assumes the working directory is this source project and reads only `tests/fixtures/invoice.py`; it does not fix the deliberately wrong fixture. A real project plan must name its exact source root and original files. The DB must be outside the bound source files and shared by controllers whose tasks need mutual exclusion. Do not place secrets or raw credential output in plans/results.
A current plan has `root`, `goal`, `backend: "native"`, `nodes`, with optional `bounds`, `routes`, `implement`, `run_id`, `capacity_scope`, `workflow`. New exec plans and `execution_pool` selections are rejected by the controller. A node requires `id`, `role`, `task`, explicit `sources`, named `checks`; optional `depends`, `writes`, `risk`, `tier`, `required`, `economy_qualified`, `ordinary_qualified`, `verifies`, `supplemental`, `snapshot_root`. A v4 `supplemental:true` node must also be optional, readonly, non-strong and non-verifying. Mainline nodes may not depend on supplemental nodes. Pending/failed/interrupted supplemental nodes do not block mainline finish, but any material evidence already returned must be dispositioned or promoted before acceptance. Status reports mainline completion and supplemental coverage separately. There are no executable tool instructions or arbitrary CLI flags in the schema. Unknown fields, duplicate JSON keys, cycles, escapes, excessive depth and oversized graphs are rejected.
Sources must be explicit regular files, not directories, wildcard paths, symlinks/reparse points, hard links or credential files. Default source limit is 4 MiB per file and 128 paths per node. These conservative limits intentionally fail closed. An unavailable file is a gap, not an excuse to silently read another revision.
One deferred-binding exception permits a required writer's verifier/reviewer to declare that writer's exact not-yet-created write paths as sources. The missing paths remain unbound and cannot be dispatched. After the writer successfully completes and its execution is reconciled, Root must explicitly `refresh` the pending review to bind the created bytes. Ordinary missing sources, paths outside that writer's write set and formerly existing sources do not qualify. Final independent coverage still includes every writer source/write path.

## Routing qualification

New CLI and Python runs default to `workflow: "astra-mainline"`; the complete mainline
uses Astra. Only optional `supplemental: true` nodes may select Luna, with a matching
isolated `snapshot_root`. They cannot write, verify required work or feed mainline
dependencies. See the [v4 supplemental protocol](supplemental.md) for the full rules.
The legacy routing options described below apply only to explicit `workflow: "legacy"`
or unchanged saved 3.0.0 contracts, not as a silent fallback for new tasks.
Use the [host routing criteria](host-routing.md) to qualify each task before adding it. `ordinary_qualified: true` records Root's assessment that scope, source access, checks and capability suffice for an ordinary low/medium-risk readonly task. With no explicit `tier`, that selects `ordinary` (cwf_general, Luna/max); without qualification the conservative default remains `strong`. An explicit strong choice is preserved. This flag is a trusted planning assertion, not a model-quality measurement.
Record a recomputable or source-checkable deliverable in `task` and its actual checks in `checks` before setting that flag. When those checks cannot establish a broad defect-absence, repair-completeness or acceptance conclusion, keep that conclusion with Root/the strong route and any required capable independent reviewer. Runtime validates the declared graph, sources and results; it cannot infer that Root mislabeled a difficult task or that named checks establish semantic completeness.
The existing `economy` tier stays Luna/medium and requires a low-risk explorer with `economy_qualified: true` for mechanical work. Ordinary tasks use approved non-strong allowance only; the separately preauthorized economy reserve stays mechanical. Both count toward cumulative launches. Strong allowance remains reserved for critical work.
In legacy policy only, ordinary verifier/reviewer nodes may declare `verifies` for low/medium-risk readonly targets. They require a dependency on the target, a different host agent and matching source coverage at acceptance. A high-risk target or writer always requires a strong checker, regardless of the checker's own risk label. General and mechanical profiles grant no writing.
New default run contracts include `ordinary`; explicitly supplied old three-route contracts and saved contracts remain unchanged. Adding ordinary work to a contract without that route is rejected before admission, rather than silently inserting a model. Existing attempts retain their recorded routing and budget. No database schema migration or automatic escalation is performed.

## Native host bridge
After `next` returns `admitted: true`, use the current Codex native tool schema to launch exactly the returned task, with its selected compatible profile/model, original source identity, exclusions, checks and permissions. Root must confirm that the host can independently read the assigned source and enforce applicable sandbox rules. Python does not implement native spawn; the host is the executor.
Bind the exact returned child ID: `bind --attempt TOKEN --external-id CHILD_ID --backend native`. If dispatch may have happened but its ID is missing, retain the reserved attempt and inspect host state; never resend automatically. Only assert no launch when the host has actually confirmed it. A lost response does not refund the reserved allowance.
When the host has a terminal result, pass a UTF-8 JSON result to `complete --attempt TOKEN --external-id CHILD_ID --backend native --result result.json`. Required fields: `outcome`, `summary`, `sources_opened`, `checks`, `changed_files`, `claims`. Checks contain exact `name` and `status`; claims contain `proposition`, `evidence`, `existence`, `applicability`, `impact`. All opened/evidence paths refer to the assigned source list. Full schema: `scripts/cwf_runtime/result.schema.json` in the Skill root. Do not translate an unrun or failed check into PASS.
`complete` records the result and retains execution and host-resource holds. The default `release --attempt TOKEN --external-id CHILD_ID --confirmed --reason "actual host observation"` still requires actual host closure/termination plus effect inspection. It confirms host-resource release. A timeout, interrupt request, elapsed deadline, agent self-report, or stopped Root shell is insufficient. The same native child identity cannot satisfy its own non-author verification under another node ID.

For a successfully completed **native readonly** attempt, the current collaboration adapter also accepts `release --attempt TOKEN --external-id CHILD_ID --confirmed --kind readonly-turn-completed --receipt observation.json --reason "host completed observation and settled tools"`. Root must first read that exact agent's current `collaboration.list_agents` status, correlate it with the accepted attempt result, and verify all task-owned tool calls/processes have settled. Do not send outside follow-ups or reuse the agent between this observation and reconciliation. The normalized UTF-8 receipt is:
```json
{"attempt":"TOKEN","external_id":"CHILD_ID","status":"completed","observed_via":"collaboration.list_agents","observed_at":"ACTUAL_UTC_OBSERVATION_TIME","tools_settled":true}
```
This is trusted controller attestation, not a cryptographically verified receipt or permission supplied by the child. Missing, ambiguous, stale or agent-authored observations do not qualify. `observed_at` must be an ISO 8601 UTC timestamp at or after Runtime accepted completion and no later than the controller's current time; Root therefore observes host status again after `complete`. The completion-time comparison allows only one microsecond of receipt precision plus one floating-point ULP of representation error, accommodating Windows clock ticks; future observations receive no added tolerance. Identity, accepted result, read-only scope, unchanged source and settled tools are checked before appending `attempt.readonly_turn_completed`. Exact retries are idempotent; conflicting receipts are rejected. No execution token or budget is refunded.

The readonly receipt reconciles **execution only**; it leaves `attempts.released=0` and host-resource reservations intact. It can unblock a later source writer only after the readonly execution is settled. Writer, exec, failed, partial, interrupted, unknown, unbound and active attempts cannot use this path. Retry/resume retain their existing strict resource-reconciliation requirements. A later real resource-closure receipt may still use the default release path.

`budget.execution_holds` counts unreconciled execution. `budget.host_resource_holds` and its compatibility alias `active_holds` retain conservative per-attempt reservations, not a measured number of physical sessions. Explicit `bounds.capacity` still counts these reservations; `capacity:null` adds no controller cap, so Root obeys actual host admission/queue behavior. Status reports `host_resource_state: UNKNOWN` until all resource releases are confirmed. A readonly execution can therefore complete with zero execution holds while resource cleanup remains unverified. Report these as separate acceptance results; never infer released host slots from `completed`.

Local CLI 0.153.4 schema and the [official app-server protocol](https://learn.chatgpt.com/docs/app-server#turn-events) distinguish turn completion from [thread closure](https://learn.chatgpt.com/docs/app-server#unsubscribe-from-a-loaded-thread). The current collaboration surface exposes completed status and follow-up reuse, but no close tool. App-server definitions describe the distinction; they do not prove this session's collaboration transport or exact slot reclamation timing.
High-risk tasks without a `verifies` target and every writer need a declared required strong verifier/reviewer depending on the target via `verifies`. A declared verification node does not recursively require another checker. Final acceptance checks source coverage and candidate equality; it is not a model-quality guarantee. Root must additionally judge whether the named checks actually establish the user's acceptance criteria. Independent agents must not merely report that they read the file.

## Historical exec records
The current controller rejects `exec-one`, `luna-pool`, exec admission and new exec plans before model dispatch. The model-smoke scripts also reject the native-only policy before creating output or calling a model. Use native host tools for all current Luna and Astra work.
Historical exec DB records, source modules and deterministic adapter regressions remain intact for inspection and compatibility; they are not an active dispatch route. Read their existing status/events/claims and reconcile genuinely observed prior ownership without rewriting contracts, refunding calls or inventing cleanup. Old reports describe historical tests, not current execution policy.

## Writes, source changes and evidence
All controllers that require coordination must use the same local DB. Its writer exclusion is cooperative: commands outside the runtime, independent DBs, links introduced after validation and untrusted host tools are outside this boundary. It is not a file-system security sandbox. The host must serialize relevant external edits and inspect the complete actual diff, not merely the files claimed by the child.
A writer has one closed write set and a bound original candidate; observed changes within those bound files must equal its reported `changed_files`. No automatic reset/rollback of source occurs. Readonly nodes reject unexpected candidate drift. A prepared review node must use `refresh --run RUN_ID --node REVIEW --reason "bind post-write candidate"` after the writer stops; only never-executed pending nodes may refresh. Executed evidence is never rebound in place.
Earlier exploration may become historical after a causal descendant writer changes its files. Final reports explicitly classify this as historical evidence, not proof about the new bytes; unexplained external drift still blocks acceptance. High-risk material claims require an independent capable checker on the applicable candidate. An old failed attempt's claim cannot borrow acceptance from a later retry. Fixes requiring a new candidate must be represented by new nodes, not fabricated success or writer replay. Every non-supplemental admitted graph node must complete before close. v4 supplemental nodes are deliberately nonblocking after their execution is reconciled: pending, failed, partial or interrupted supplemental work remains truthfully visible in status but does not hold mainline completion. This exception never applies to required/mainline work and cannot be used to waive a mandatory verifier or acceptance check.

## Recovery and completion
`status`, `events` and `claims` open the database read-only, never creating a missing DB. They show observed drift, historical evidence, active/unreleased attempts and unknown usage. `incomplete_nodes` lists unfinished scope with its supplemental flag; `mainline_complete` describes structural mainline completion; `scope_complete` retains all-node coverage semantics. `mainline_accepted` additionally requires current evidence, normal quality gates, received-claim triage and a matching acceptance receipt. `supplemental_coverage` separately reports launched/attempts/completed/omitted/unfinished and actual states. `current_evidence_valid` requires at least one completed evidence node and no detected drift; it does not certify whole-run success. Events are append-only via normal APIs/SQL triggers; they are not cryptographically tamper-proof against the DB owner. Journal/transaction state and admissions commit together.
`cancel --run RUN_ID --reason ...` stops new admissions and cancels pending work. Active native tasks still require real interruption/closure via host tools followed by confirmed release. An already admitted result may be retained as historical task evidence after cancellation, but the run cannot become completed.
`retry --run RUN_ID --node NODE --reason ...` requeues a released readonly failed/interrupted attempt only on the same source identity, retaining consumed budget and history. `resume --run RUN_ID --contract-hash HASH --reason ...` performs equivalent explicit recovery across a reopened readonly run after all host activity is reconciled. Root must recheck current host tools, model/effort and sandbox against the declared contract; a stored hash alone does not attest the outside environment. Expired deadlines need an explicit `--extend-deadline-seconds` grant; allowances and route/permission identity are not reset. Any already-executed writer blocks automatic mixed-run recovery.
`decide --claim CLAIM_ID --disposition ADOPT|REJECT|UNKNOWN|contested --reason ...` is a controller decision, not a child action. `finish --run RUN_ID` first accepts a nonempty complete Astra mainline with matching evidence, reconciled mainline attempts and received-claim triage. Pending probes become omitted. If supplemental execution is still active, the run remains open with `mainline_accepted: true`; no further probes are admitted. Late new claims invalidate that acceptance. After actual execution reconciliation and any new triage, another finish closes the run. Unknown host-resource cleanup remains separate. Legacy contracts keep their original all-node finish gate.
Initial v4 bounds: capacity null (no additional controller ceiling; Root obeys actual host capacity), approved launches 28, cumulative economy reserve 4, absolute launches 32, strong launches 8; planning additionally targets up to 12 supplemental Luna launches with a three-probe meaningful-task floor, graph nodes 64, dependency depth 6, attempts per node 3, deadline 1800 seconds. These are upper bounds, not targets. Required pending checks reserve approved/strong slots atomically; failed attempts are not refunded. There is no hard token/currency cap or automatic budget extension. Root separately accounts for its own observed/unknown usage.

## Validation limits
The supplied unit/integration tests use real SQLite and harmless local process fixtures plus injected executor transports; they never launch paid models by default. A simulated native receipt is not a native model launch. Live Codex/native smoke and non-author model review must be recorded separately. Consult this project's actual v3 reports before treating this first version as a live-integration-validated stable release.

## v3.0.0 reviewed effect and protocol boundaries

Runtime writer packets explicitly prohibit deletion. If a bound existing file is deleted, completion records the actual effect as partial with blocked_effects; it does not restore files, pretend completion, or retry the writer. Deletions and their special absence-based review protocol require manual reconciliation outside this first Runtime release.
Every exec response must belong to one ordered turn.started / item results / turn.completed sequence. A stale successful turn cannot certify a later incomplete turn. Unknown event schemas fail closed. Process cleanup runs on every exit path, including normal foreground completion and stream-limit failure. Windows job accounting must report zero active processes; POSIX must confirm the exact owned group no longer exists. If a POSIX group remains observable (including unreaped descendants), the adapter conservatively retains its hold and reports uncertainty, not successful release. Descendants deliberately escaping a POSIX process group are outside this cooperative process-control boundary; actual sandboxing is still required.
Multi-stage graphs retain independent verification of each stage candidate; only explicit descendant writes may explain historic source changes. Dependency readiness and final quality gates use the same history rule. A prior claim decision still requires a current candidate and cannot silently become a statement about later bytes.

The default writer lock is conservative across the entire coordination DB, including different roots/worktrees. This avoids treating distinct checkout paths as permission for parallel same-repository writes. Separate DBs and outside tools remain outside its boundary. If a terminated exec result is malformed and its source cannot be read while recording failure, the attempt is still released as interrupted/unaccepted; the source error and consumed budget are retained, never reported as successful work.
