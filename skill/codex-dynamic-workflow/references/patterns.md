# Dynamic shapes, not mandatory stages

Pick the useful shape for the current evidence gap; change it when results warrant.

| Shape | Use | Avoid |
|---|---|---|
| Solo | One bounded task; coordination adds no value | Spawning to meet a quota |
| Fan-out | Independent ready questions or evidence methods | Repeating the same search with more agents |
| Pipeline | Each item can independently move to verification | Waiting for unrelated siblings |
| Expand | New evidence identifies a distinct missing question | Renaming repeated work to reset budget |
| Compare | A genuine unresolved design choice | Scoring a decision the user already made |
| Write/review | An authorized implementation objective | Starting writes from an audit-only request |

A Map brief can orient a repository audit, but is not always required. Where multiple
branches need a shared map, finish that dependency first. The map gives original
entry points and known constraints, not conclusions the branches must trust.

## Example: evidence changes the next step

Root binds the candidate and scopes independent API/config investigations. The API
branch returns a suspected mismatch. Root checks the original API path, then starts
its independent verification while config analysis continues. A genuine contract
ambiguity can justify reading the versioned upstream contract. A confirmed issue
can enter decided implementation only when the user authorized a fix.

If the target is read-only review, report the finding and remediation plan; do not
invent write permission. If implementation is authorized, finish scoped change,
focused tests and a non-author review, adding a repair node only for an actionable
finding. A code change that affects an in-flight reader needs serialization or a
verified immutable snapshot; pipeline latency never outranks evidence consistency.

## Example: raw-source independent check

Give the verifier a neutral proposition, candidate identity, actual source paths,
relevant constraints and the question "can this behavior occur under these inputs?".
Do not give it "prove the finder right" or the Root's intended verdict. Let it open
necessary raw dependencies within scope. Missing access yields a specific gap.

## Failure and completeness

On failed tool/environment input, retain completed evidence and the exact failure.
One repair with a concrete changed input can be worthwhile within the run allowance;
"try harder" is not a changed method. A failed writer is inspected before any retry.
A coverage critic may check the planned inventory against examined scope when needed,
but cannot turn an incomplete audit into complete merely by returning no findings.

Claims rejected with evidence stay recorded. An audit with unexamined material scope
is incomplete even when every examined claim was rejected. No automatic fourth wave,
mandatory panel, irreversible Sol disposition or old Fleet headcount survives.
