# Dynamic shapes, not mandatory stages

Pick the useful Astra-led mainline shape; change it when results warrant. Add at least three
distinct optional Luna directions on meaningful tasks when capacity permits. This is
per task, not per file or repair cycle. Fewer real directions or host/budget constraints
are disclosed; probes are never a completion barrier. See [supplemental](supplemental.md).

| Shape | Use | Avoid |
|---|---|---|
| Solo mainline | Astra handles a cohesive task end to end | Moving required work into optional Luna probes |
| Fan-out | Independent ready questions or evidence methods | Repeating the same search with more agents |
| Pipeline | Each item can independently move to verification | Waiting for unrelated siblings |
| Expand | New evidence identifies a distinct missing question | Renaming repeated work to reset budget |
| Compare | A genuine unresolved design choice | Scoring a decision the user already made |
| Write/review | Astra brief, coherent Sol implementation/tests, targeted Luna evidence, Astra acceptance | Duplicate Astra implementation or Sol self-approval |

## Mainline staffing and review

In Skill-only mode, Root can keep cohesive mainline work in its own thread, including
necessary direct work when delegation adds no value; normally Sol owns implementation/tests.
Runtime-managed work still requires an admitted packet;
do not move a managed step outside its ledger to bypass a gate or exhausted budget.
Native Astra children are useful for independent
deliverables or necessary non-author checks, not to fill every named role. Do not add
a mapper, planner, writer and integrator merely because a diagram contains those roles.
The three-probe intent applies to supplemental coverage, not mandatory mainline staffing.

Do not attach an Astra reviewer to every Luna report or recursively review every reviewer.
This does not waive required writer, high-risk or user-requested independent checks.
For the same obligation and candidate, reuse adequate non-author review on unchanged
applicable evidence; a new promotion still requires its own explicit resolution.
Refresh affected coverage after a fix or counterevidence, not after every status update. Root counts as
a writer. Self-review at a higher effort is still self-review, not independent evidence.

## Bounded probe examples

Examples, not a mandatory task list or pre-established findings. Adapt the three
directions to the actual task; do not run the same broad scan under three role names.
Use existing task/scope/check fields: one question and possible decision impact, raw
entry points with exclusions, and a coverage/deadline stop. This is prompt guidance,
not a new Runtime schema or a mandatory form.

| Direction | Concrete question | Evidence and bounded stop |
|---|---|---|
| Coverage | Within the assigned module and allowed direct callers, is a configuration or call path missing from the proposed coverage? | Return the overlooked path and source reference, or the examined set and remaining gap; stop at the assigned scope/deadline. |
| Counterexample | Under the named state transitions, can cancellation, retry or a late result break the stated invariant? | Return a concrete sequence and original evidence, or the cases actually examined; do not invent a counterexample or run unsafe effects. |
| Test gap | Do the named tests distinguish correct behavior from the competing explanation for this change? | Return the missing assertion/input and why it matters, or bounded negative coverage; suggestions are not executed tests. |

Give useful findings back early through actual supported parent communication. A clean
result is valid only for examined scope. A missing source or insufficient capability is
a gap, not permission to expand, spawn peers, fake completion or discard a risk.
Keep all potentially material leads in CLAIMS even when only three cards lead the summary.

A Map brief can orient a repository audit, but is not always required. Where multiple
branches need a shared map, finish that dependency first. The map gives original
entry points and known constraints, not conclusions the branches must trust.

## Example: evidence changes the next step

Root binds the candidate and scopes independent API/config investigations. The API
branch returns a suspected mismatch. Root checks the original API path, screens the
candidate, and starts independent verification when required by its impact or the
acceptance contract while config analysis continues. A genuine contract
ambiguity can justify reading the versioned upstream contract. A confirmed issue
can enter decided implementation only when the user authorized a fix.

If the target is read-only review, report the finding and remediation plan; do not
invent write permission. If implementation is authorized, finish scoped change,
focused tests and a non-author review, adding a repair node only for an actionable
finding. A code change that affects an in-flight reader needs serialization or a
verified immutable snapshot; pipeline latency never outranks evidence consistency.

## Example: raw-source independent check

Give the verifier a neutral proposition, candidate identity, actual source paths,
relevant constraints and the question "can this behavior occur under these inputs?".
Do not give it "prove the finder right" or the Root's intended verdict. Let it open
necessary raw dependencies within scope. Missing access yields a specific gap.

## Failure and completeness

On failed tool/environment input, retain completed evidence and the exact failure.
One repair with a concrete changed input can be worthwhile within the run allowance;
"try harder" is not a changed method. A failed writer is inspected before any retry.
A coverage critic may check the planned inventory against examined scope when needed,
but cannot turn an incomplete audit into complete merely by returning no findings.

Claims rejected with evidence stay recorded. An audit with unexamined material scope
is incomplete even when every examined claim was rejected. No automatic fourth wave,
mandatory panel, irreversible Sol disposition or old Fleet headcount survives.

For implementation use [delegation](delegation.md): a sufficient brief, one scoped Sol
writer, then Astra acceptance against the original goal and full diff. One Luna
counterexample direction should challenge the design itself when useful, not simply
check conformance. Do not reopen three probes at each stage. A plan contradiction
needs a concrete escalation; routine commands and in-scope test repair stay with Sol.
