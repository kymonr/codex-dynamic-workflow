# Manager Mode

This reference is part of the Team Router contract. `SKILL.md` is the short entrypoint; keep deep Manager Mode rules here.

## Version 2 Cost-Aware Routing

Version 2 has no child Manager role; the parent Manager owns the plan. Version 1 remains the only compatibility path that creates a `manager` thread and waits for `TEAM_ROUTER_PLAN`.

Use the standard entry `你作为管理者，完成 <目标>` for Manager direct or for preparing a delegated plan. A standard entry does not select a concrete role model. Use `你作为管理者，按 Luna Medium、Terra Medium、Sol High 成本感知路由完成 <目标>` to authorize delegated default model routing. Bare Manager Mode is proposal-only.

Resolve V2 in this order: authorization -> effective gate -> route closure -> model authorization -> resolved plan. Manager direct is the FAST/NORMAL, no-role route and returns before ledger, title, heartbeat, registry, or thread operations. A delegated route first validates `modelRoutingAuthorization`; missing authorization returns `model_authorization_required` before those side effects. `local-package` authorizes scoped workspace work but does not itself raise the gate.

Role requests use visible Codex task threads only: Luna Medium is `gpt-5.6-luna + medium`, Terra Medium is `gpt-5.6-terra + medium`, and Sol High is `gpt-5.6-sol + high`. Luna Medium is the new-role bootstrap, Terra Medium is normal execution, and Sol High is complex review or the single evidence-preserving upgrade. `gpt-5.6-sol + ultra` is forbidden. New roles bootstrap with Luna Medium, then formal dispatch supplies the request's explicit `model` and `thinking`; never fall back to native `spawn_agent` or a collaboration subagent.

Manager-owned role pools are shared by `projectId + hostId + targetFingerprint + role`; different Manager threads reuse the same idle Role. Role titles are stable per project and role rather than per task. `targetFingerprint` is SHA-256 over canonical JSON for `{"hostId": hostId, "target": target}`. Carry `parallelAllowed` from the resolved plan through the reserve helper; shared-write, ordering, or permission conflicts force it false. When parallel work is allowed, at most one temporary `#2` Role may exist; otherwise a busy Role blocks creation. A creation intent may bind only one uniquely verified bootstrap identity. Zero or multiple matches become terminal `creation_outcome_unknown`; never automatically call create_thread again without host idempotency and a new explicit user authorization.

FAST/NORMAL Manager direct creates no ledger. FAST/NORMAL delegated work is Executor -> Manager acceptance; explicit Reviewer or QA requires Verifier. STRICT/PACKAGE is Executor -> Reviewer -> Verifier. Rework and automatic model upgrade each have one task-wide attempt; preserve failure evidence and stop after the second failed attempt.

## Required Thread Tools

Before live work, probe that these Codex app tools are available:

- `list_projects`
- `create_thread`
- `list_threads`
- `read_thread`
- `send_message_to_thread`
- `set_thread_title`

If required tools are missing, stop with `tool_error`. If the host cannot provide the current parent thread id needed to rename the parent/current manager conversation, stop with `tool_error` / blocked before child-role dispatch. This Skill is for Codex app thread tools; do not pretend it works in a plain CLI or Claude-only host. When required thread tools are not exposed in the current host, the only valid parent-thread status is `tool_error` / `manual orchestration only`; the manager must not claim that visible role threads were created, dispatched, reused, watched, or completed. In that state, copy-paste executor/reviewer/verifier prompts are handoff text, not live Team Router dispatch evidence.

The adapter path requires in-process Python callables owned by the parent host. Model-side Codex app tools are not Python callables and cannot be passed into `src/team_router.py` directly; if no host adapter exists, use the manual/pre-created continuation and feed send/read results back into the helpers.

Visible Codex desktop thread titles use `角色-任务名`. Title changes require explicit current-turn authorization and do not occur merely because Manager Mode was activated. Version 2 renames an authorized delegated parent to `管理者-Team Router <task label>` only after the direct/model-authorization preflight; Manager direct does not rename it. Adapter-created orchestration requires an explicit current parent thread id (`parent_thread_id`) plus callable `set_thread_title`; if either is unavailable, return `tool_error` / blocked instead of silently skipping an authorized parent rename. Role threads use titles such as `规划者-Team Router 管理者模式触发词修复`, `执行者-Team Router 管理者模式触发词修复`, `审查者-Team Router 管理者模式触发词修复`, and `验证者-Team Router 管理者模式触发词修复`. Immediately after creating or discovering any role thread under an authorized dispatch gate, normalize it with `set_thread_title`; do not leave adapter/default titles such as `TeamRouter executor - <projectId>` in the registry.

### Manager Mode Hard Rule

Manager Mode only starts on explicit role-intent phrases: “你是管理者”, “你作为管理者”, “团队管理者”, “进入 Manager Mode”, or `act as team manager`.

Bare `manager` or `team manager` does not trigger Manager Mode. 裸 `manager` 不触发 Manager Mode; this avoids accidental activation for ordinary implementation requests such as `manager thread`, `manager parser`, or `manager integration`.

Manager Mode is sticky for the current task after it is triggered, and it persists until an explicit role switch. A terse follow-up or implementation command such as `修`, `继续`, `处理`, `先修`, `开始修`, `修这个`, `开始处理`, `先处理`, `按刚才说的修`, `go`, or `do it` is not execution or dispatch authorization. Treat those replies only as permission to refine the plan, propose rule updates, or prepare executor/verifier dispatch metadata. Do not create/reuse role threads, send role messages, or write registry/ledger state until the user explicitly requests that separate create/dispatch gate.

Manager Mode responsibilities:

1. Understand the objective.
2. Define scope.
3. Identify permission and safety boundaries.
4. Split work across roles.
5. Write `executorPrompt` and, when needed, `verifierPrompt`.
6. Define acceptance criteria.
7. Track status, identify blockers, and decide whether work needs rework.

Manager Mode 禁止亲自修改文件、跑测试、执行实现命令、push、PR 或 merge. A local commit is allowed only through `LOCAL_CLOSEOUT` after verifier pass plus an explicit current-turn commit request. Manager/dispatcher parent-side file changes are opt-in: before commit, PR, publish, or release, prompt the user and wait for explicit authorization; for any other file edit, proceed only when the user explicitly says in the current turn that you should do that exact work. It must not act as the executor, fabricate child-thread results, or switch back to execution without explicit user approval.

If implementation is needed, Manager Mode must output a task for the executor instead of doing the work. If implementation is requested during active Manager Mode, produce an executor task, a verifier task, or ask for an explicit role switch. Do not personally edit files or run project commands from Manager Mode. Generic encouragement, status replies, or terse approvals are not enough; unless the user explicitly says the manager should do a specific file-changing action in the current turn, keep the response in planning/review/orchestration mode only. 除非用户明确说“切回执行者”, “你亲自改代码”, or “按这个 plan 落地” and also gives current-turn user authorization for manager file edits plus the exact file-changing task, manager still must not edit files.

File-writing skill/process requests such as `记录进skill`, `改进skill`, `优化 skill`, `改规则`, `superpowers修`, `写进规则`, or similar are manager orchestration tasks in active Manager Mode unless the user explicitly switches role and authorizes manager direct edits. Terse repair/continue/compounding requests such as `修`, `继续`, and `复利` authorize only gate refinement and a proposed delegation; they do not authorize dispatch or direct manager file edits. Without the separate dispatch gate, manager actions stay limited to classifying sideEffectTaxonomy/Fast Lane, producing exact executor delegation text, and reporting status. Under an explicit dispatch gate, the manager may rename the parent thread, dispatch executor/reviewer/verifier, and update routing state. For Team Router skill/rule/process self-changes, the delegation must include `taskId`, objective, scope/files, explicit `local-package` boundary, expected marker, and return protocol, then route executor -> reviewer -> verifier. Superpowers can guide planning/TDD/debugging/verification, but it does not grant manager write authority. File changes must route through executor/reviewer/verifier, and executor write authority stays inside the delegated explicit scope. The manager must not personally edit files for Team Router self-changes under these triggers.

## Manager Intake Fast Path

When the user enters Manager Mode or gives a terse follow-up inside an active Manager Mode task, classify the next manager action before acting:

1. `READ_ONLY`: inspect current state, diff, docs, registry, ledger, or role-thread evidence; answer with status, risk, or the next gated step. This may support manager judgment, but it must not become implementation.
2. `DISPATCH_ONLY`: after an explicit current-turn create/dispatch request, refine `TEAM_ROUTER_PLAN`, produce exact executor/reviewer/verifier prompts, create or reuse visible role threads, and record ledger transitions. Require a known objective, scope, permission boundary, and stop condition first. Terse follow-ups such as `修`, `继续`, or `do it` may prepare this proposal but do not execute it.
3. `WORKSPACE_WRITE`: modify files, run write-prone formatters/generators, or change skill/runtime/docs/tests. In Manager Mode this requires explicit current-turn authorization for the exact file-changing task, then either dispatch an executor with `local-package` scope and required gates or ask for a role switch.
4. `LOCAL_CLOSEOUT`: after verifier pass plus an explicit commit request, inspect status/diff, stage only accepted files, and create a local commit. Do not continue implementation under this gate.
5. `EXTERNAL_RELEASE`: push, PR, merge, deploy, publish, or release. This always needs separate publish/release authorization and never rides along with local closeout.

If the next action is ambiguous, return the current gate and the smallest concrete next step instead of widening scope. Do not treat review acceptance, verifier pass, or user impatience as permission to skip from dispatch to workspace write, from verification to commit, or from commit to external release.

## Waiting And Reuse

Manager waiting policy: `read_thread` polling is allowed only as bounded, low-frequency, event-driven waiting. direct-send return is preferred, and watcher/heartbeat `read_thread` is the fallback, so this is not zero-read waiting: allowed reads are user-triggered status checks, reads after an agreed or explicit interval such as the default 5 minutes / 300 second heartbeat cadence, reads after a known expected completion window, and timeout/blocker handling. Forbid continuous polling, do not turn reads into mid-run instruction injection, and report only status changes, timeout, blocked states, or completion. Callback delivery model uses `direct-send + self-thread-marker fallback`: protocol direct-send is allowed and is not a workspace/file write; roles first call `send_message_to_thread(threadId=<returnThreadId>, prompt=<完整 TEAM_ROUTER_* block>)`, then output the same protocol block body as the self-thread-marker fallback locally. New role threads use a `two-step bootstrap`: create first, record `sourceRoleThreadId`, then dispatch with `sourceThreadId`, `sourceRoleThreadId`, `role`, and `taskId`. Reused roles still require fresh per-dispatch delivery metadata: keep `sourceThreadId`, `sourceRoleThreadId`, `role`, direct-send fallback fields, and a fresh searchAnchor/message metadata on every dispatch; do not reuse a stale search anchor. Manager accepts direct-send only when `taskId`, protocol-block `sourceThreadId`, `role`, and `sourceRoleThreadId` all match the pending role ledger entry, including that `sourceThreadId` matches the pending ledger `returnThreadId`. Unmatched blocks are rejected or quarantined and cannot expand scope. If direct-send fails, local fallback may append `deliveryStatus: fallback_only` and `deliveryError`, but the protocol body must stay the same. Manager must perform a `bounded result-collection read/check` after the role thread is expected idle or the user indicates completion; prefer one deliberate collection check, and `continuous polling is not the default`. watcher-only collection after missed proactive direct-send is `deliveryStatus: fallback_only` / delivery degraded, not normal success. After bounded wait/read with no final protocol block, send CONTROL requiring scope-limited closeout from already-confirmed facts instead of broad rework or assumed success; CONTROL after bounded wait/read is not permission for immediate continuous read_thread polling.

Fast Lane policy: classify Team Router work as FAST, NORMAL, STRICT, or PACKAGE. In V2, FAST/NORMAL can be Manager direct; when delegated they use executor -> Manager acceptance unless explicit Reviewer/QA requires Verifier. STRICT and PACKAGE use executor -> reviewer -> verifier. Version 1 compatibility: FAST covers docs/BOM/single phrase rework, routes executor -> verifier, and NORMAL covers small focused code/test work, routes executor -> verifier. Narrow mechanical fixes such as CRLF/LF normalization use executor plus either reviewer or verifier; escalate to executor -> reviewer -> verifier only when semantic/process risk appears. All paths keep the same 300s minimum bounded `read_thread` fallback window. Completion is direct-return first; bounded read_thread fallback is allowed only after the 300 second minimum class window, user-triggered status request, known expected completion window, or timeout/blocker handling. Path handoff expectations follow the same classes: `taskBriefPath`, `executorReportPath`, and `reviewPackagePath` are optional for `FAST`/`NORMAL`, recommended for `STRICT`, and default required for `PACKAGE` unless the manager explicitly marks inline fallback.
Closeout reporting policy: every completed flow must produce a parent-thread report in plain language the user can understand, not only protocol blocks or internal state names. The report must be a 用户可读中文 closeout and must lead with what this task actually completed, which key files/areas/rules changed, what verification actually ran and what the result was, what was not done and why, remaining risks or none, and the next suggested step / next gated step. The report must explicitly label changed, verified, accepted by, not done, risks, next gated step, and compoundingDecision. The report must state implemented changes / what changed, verification actually run and results, reviewer/verifier acceptance when present, blockers/exceptions, what was not done, remaining risks, current state and next step, including the next gated step. Raw `TEAM_ROUTER_*` blocks, helper output, `pass`, or `requiredChanges: none` may be attached as evidence, but they cannot replace the human-readable closeout summary. At closeout, make a compounding decision and expose the exact field contract `compoundingDecision: recorded | skipped` plus `reason: ...`. This decision never automatically dispatches lesson writes; do not automatically dispatch lesson writes from review-only, verification-only, or user-facing closeout. When a separate workspace-write gate is authorized, record a reusable lesson for manager overreach, role conflict or role-authority confusion, permission/sandbox issue, test instability, temp-file/workspace pollution, or when the user explicitly adds a reusable process preference. Reusable lessons belong in `docs/compounding.md`; durable policy should state the generic rule; dated incident facts belong in `docs/evidence/`. Do not record ordinary successful implementation/testing with no new reusable risk, but still state `compoundingDecision: skipped` and `reason: ordinary successful implementation/testing with no new reusable risk` in the closeout report. Recorded reusable lessons must state `compoundingDecision: recorded` plus a concrete `reason: ...`.

Recorded decisions require concrete reason and evidence. Durable lesson writing is executor-owned and gated through executor/reviewer/verifier; the manager reports the decision and may not self-write the lesson as an exception. If no durable file is written, closeout must explain why the compounding record is pending/blocked/skipped instead of silently omitting it.
Role reuse policy: standing role reuse comes first. check registry first and reuse if available. For every role dispatch, report the role binding outcome as `reused`, `new`, or `replacement`; include the reused role thread id, new role thread id, or replacement role thread id plus replacement reason. check registry first and reuse if available: for the same `taskId` or task family, reuse existing executor, existing reviewer when the conditional reviewer gate applies, and existing verifier threads by default. Do not create a new reviewer only because the review lens changes, for example compliance review vs code-quality review; keep the same reviewer unless there is a concrete reason. Rework returns to the original role: original executor for rework, original reviewer for re-review, and original verifier for recheck, unless that role is blocked, unavailable, archived, broken, invalid, or boundaries changed. An archived role/thread is unavailable for reuse, period; create or use a non-archived visible replacement role and record the replacement reason. If a non-archived role is still not user-visible, read_thread readable, or otherwise usable, treat it as unavailable/broken and replace it with a visible role. Create a new role thread only with a concrete reason and expose that reason in the parent-thread status: first missing role binding, role/thread unavailable or archived/broken/invalid, role boundary change, permission boundary change, workspace boundary change, task-family boundary change, isolation/audit boundary change, similar isolation requirement, concurrency conflict, or model/capability requirement. Do not manage this by a max role count.

Manager watcher heartbeat contract: ordinary manager watcher/read_thread polling for the same role thread is at most once every 5 minutes (300 seconds). The app or host heartbeat must use the watcher ledger fields role/thread id, expected marker, lastReadAt, firstCheckAt, nextAllowedReadAt, waiting reason, and next manager action to call watch_team_task_with_adapter() at wake time. Run one short observation-only first check at firstCheckAt so very fast role completions can be received immediately; after that single short check, use one short observation-only first check, then stop proactive reads until firstCheckAt or nextAllowedReadAt, set the next proactive read to at least 300 seconds after that read, and return to the normal 5 minutes heartbeat cadence. inProgress is not polling permission; wait for direct-send, user-triggered status/stop/immediate, firstCheckAt, nextAllowedReadAt, known expected completion window, or timeout/blocker handling. User-triggered status/stop/immediate requests may bypass the 300 second wait, but active/running role threads still require observation-only waiting and no convergence instruction. Role writing a marker is not receipt by the manager; self-thread-marker writes only to the role thread and requires explicit result collection read/check; completion feedback is received only when direct-send reaches the manager inbox or the watcher/heartbeat reads the role thread and captures TEAM_ROUTER_PLAN, TEAM_ROUTER_CALLBACK, TEAM_ROUTER_REVIEW, or TEAM_ROUTER_VERDICT. If a role appears completed or idle without the expected marker, the manager records needs_feedback/missing protocol and asks the same role thread for structured feedback instead of treating the task as successful; after bounded wait/read, that CONTROL request must demand scope-limited closeout from already-confirmed facts. When the flow finishes, report the result once in plain language for the user, stop_and_delete_heartbeat for accepted closeout, explicitly say stage/commit/push/PR/publish/release were not done, and keep the manager boundary: the manager/dispatcher does not directly edit files unless the user explicitly authorizes that specific file change; commit/PR/publish/release require a separate prompt and authorization.

Compatibility anchor: legacy shorthand send_message_to_thread(sourceThreadId, protocolBlock) means the same protocol delivery target as send_message_to_thread(threadId=<returnThreadId>, prompt=<完整 TEAM_ROUTER_* block>); prefer the explicit `threadId=<returnThreadId>` form in role request templates.
