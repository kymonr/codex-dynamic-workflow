# Manual Orchestration

This reference is part of the Team Router contract. `SKILL.md` is the short entrypoint; keep manual/pre-created orchestration details here.

## Version 2 Manual Boundary

Manual tools do not weaken Version 2 preflight: the parent Manager must decide Manager direct before any ledger, title, heartbeat, or thread action. For a delegated plan, require explicit model-routing authorization, derive `targetFingerprint` from canonical target plus host, and use a visible Codex thread with explicit model + thinking. New threads bootstrap on Luna Medium; formal dispatch selects Luna/Terra/Sol as resolved. Never use native `spawn_agent` fallback.

Manual recovery reads `list_threads` plus `read_thread` to bind exactly one bootstrap identity. A zero or multiple match is terminal `creation_outcome_unknown`, retains recovery evidence, and never automatically creates another role. `parallelAllowed` stays attached to the reserve request; shared-write, sequencing, and permission conflicts force it false.

### Pre-created roles path

Version 1 compatibility: use this path when the parent thread has already called `create_thread` manually or the host cannot pass tool callables into Python directly. If required thread tools are not exposed in the current host, this file supports `manual orchestration only`: prepare copy-paste executor/reviewer/verifier prompts and package paths, but do not record or report that role threads were created, dispatched, reused, watched, or completed. Bare `create_thread` plus `read_thread` is not formal role dispatch or direct-return completion until the role is registered in the ledger and dispatched with `returnThreadId` / `sourceRoleThreadId`.

1. Probe the required tools and run `list_projects`; choose the current `projectId` and project target.
2. Resolve `stateRoot` and load the project registry.
3. V1 only: normalize the parent/current manager conversation to `调度者-Team Router <task label>` and role threads to `角色-任务名`; `TeamRouter <role> - <projectId>` is only a legacy discovery/migration alias. V2 instead uses parent `管理者-Team Router <task label>` and pooled roles `角色-Team Router <projectId>`, with at most one temporary `#2`. Then call `create_thread` only for missing core roles and add conditional roles when their gates apply. Role threads must be Codex desktop thread roles, not collaboration subagents.
4. Build a `roles` mapping with `manager`, `executor`, and `verifier`, each containing `threadId`, normalized `title`, `createdAt`, and `lastObservedAt`.
5. Persist the pre-created role bindings with `create_team_task()` or the lower-level `update_registry_roles()` plus task-ledger helpers.
6. Do not call `start_team_task_with_adapter()` after manually creating role threads.

### Manual/pre-created continuation

Use this continuation after the pre-created roles path when the parent thread directly invokes Codex app tools or the host cannot pass tool callables into Python. This path uses manual helper/record/capture functions; it does not continue through `orchestrate_team_task_with_adapter()` or `run_team_task_with_adapter()`. `parent_entry_guard(...precreated_roles...)` is only a boundary decision and prompt aid here, not an end-to-end adapter-runner entrypoint.

1. Build the manager request with `make_plan_request_message()`, call `send_message_to_thread`, normalize the send result with `thread_send_anchor()`, then persist the anchor with `record_plan_request_sent()`.
2. Call `read_thread` for the manager thread, normalize the plain result with `normalize_thread_read_messages()`, then pass messages to `capture_manager_plan_from_read()`. Do not dispatch if the plan is blocked, malformed, unreachable, or asks for escalation.
3. Build executor work with `make_executor_dispatch_message()`, call `send_message_to_thread`, normalize the send result with `thread_send_anchor()`, then persist the anchor with `record_executor_dispatch_sent()`.
4. Call `read_thread` for the executor thread, normalize the result with `normalize_thread_read_messages()`, then pass messages to `capture_executor_callback_from_read()`. If no final callback is present but the read window covers the anchor, leave the task waiting and give the user a copy-paste reminder for the executor thread.
5. Build verifier work with `make_verifier_request_message()` using the raw executor callback block, call `send_message_to_thread`, normalize the send result with `thread_send_anchor()`, then persist the anchor with `record_verifier_request_sent()`.
6. Call `read_thread` for the verifier thread, normalize the result with `normalize_thread_read_messages()`, then pass messages to `capture_verifier_verdict_from_read()`.
7. Load the project registry and emit `format_task_update_for_user()` to the user. Do not replace it with an unstructured summary.

Executor work is complete-outcome delegation: the role independently performs understand, internal plan, RED, implementation, focused tests, and self-review before one terminal return (`done`, `needs_feedback`, or `blocked`). The Manager must not drive it with continuation prompts or micro-dispatches. When host write capability fails, preserve the exact error and require `blocked + zero-write + clean worktree`. Manager broker-recovery is exceptional and explicit; it cannot be reported as Executor success, parallel writer success, isolated-worktree write, or hard permission.

After dispatching a role thread, do not continuously poll it. direct-send return is preferred when available, and watcher/heartbeat bounded status reads are the fallback, but only when user-triggered, after an agreed or explicit interval, after a known expected completion window, or for timeout/blocker handling. A `read_thread` check is observation, not a channel for mid-run instruction injection. Manual role return still uses `direct-send + self-thread-marker fallback`: protocol direct-send is allowed and is not a workspace/file write; roles first call `send_message_to_thread(threadId=<returnThreadId>, prompt=<完整 TEAM_ROUTER_* block>)`, then output the same protocol block body as the self-thread-marker fallback locally. New role threads use a `two-step bootstrap`: create first, record `sourceRoleThreadId`, then dispatch with `sourceThreadId`, `sourceRoleThreadId`, `role`, and `taskId`. Manager accepts direct-send only when `taskId`, protocol-block `sourceThreadId`, `role`, and `sourceRoleThreadId` all match the pending role ledger entry, including that `sourceThreadId` matches the pending ledger `returnThreadId`. Unmatched blocks are rejected or quarantined and cannot expand scope. If direct-send fails or was bypassed during manual collection, local fallback may append `deliveryStatus: fallback_only` and `deliveryError`, but the protocol body must stay the same. self-thread-marker writes only to the role thread and does not automatically appear in the manager/main thread; manager collection is a `bounded result-collection read/check` after expected idle or user-indicated completion, preferably one deliberate collection check, and `continuous polling is not the default`. A manager-read child-thread result is degraded/manual collection unless watcher/heartbeat capture advances the ledger; it is not normal proactive role return. After bounded wait/read with no final protocol block, send CONTROL requiring scope-limited closeout from already-confirmed facts instead of broad rework or assumed success; CONTROL after bounded wait/read is not permission for immediate continuous read_thread polling.

Fast Lane policy: classify Team Router work as FAST, NORMAL, STRICT, or PACKAGE. In V2, FAST/NORMAL read-only/design-only can be Manager direct; delegated read-only/design-only uses Executor -> Manager acceptance unless Reviewer/QA causes a Verifier closure. New FAST/NORMAL workspace writes are never Manager direct and use Executor -> Verifier. STRICT/PACKAGE uses Executor -> Reviewer -> Verifier. Persisted pre-A3 FAST/NORMAL V2 routes remain frozen unless evidence raises risk to STRICT/PACKAGE. Version 1 compatibility: FAST covers docs/BOM/single phrase rework, routes executor -> verifier, and NORMAL covers small focused code/test work, routes executor -> verifier. Narrow mechanical fixes such as CRLF/LF normalization use executor plus either reviewer or verifier; escalate to executor -> reviewer -> verifier only when semantic/process risk appears. Completion is direct-return first; bounded read_thread fallback is allowed only after the 300 second minimum class window, user-triggered status request, known expected completion window, or timeout/blocker handling. Path handoff expectations follow the same classes: `taskBriefPath`, `executorReportPath`, and `reviewPackagePath` are optional for `FAST`/`NORMAL`, recommended for `STRICT`, and default required for `PACKAGE` unless the manager explicitly marks inline fallback.
Closeout reporting policy: after `format_task_update_for_user()` or any protocol closeout, give the user a plain-language report they can understand. It must be a 用户可读中文 closeout and explicitly label changed, verified, accepted by, not done, risks, next gated step, and compoundingDecision. Include implemented changes, verification actually run and results, reviewer/verifier acceptance when present, blockers/exceptions, what was not done, remaining risks, current state and next step, including the next gated step. Also make a closeout-time compounding decision and expose the exact field contract `compoundingDecision: recorded | skipped` plus `reason: ...`: record a reusable lesson for manager overreach, role conflict or role-authority confusion, permission/sandbox issue, test instability, temp-file/workspace pollution, or when the user explicitly adds a reusable process preference. Reusable lessons belong in `docs/compounding.md`; durable policy should state the generic rule; dated incident facts belong in `docs/evidence/`. Do not record ordinary successful implementation/testing with no new reusable risk, but still state `compoundingDecision: skipped` and `reason: ordinary successful implementation/testing with no new reusable risk` in the closeout report. Recorded reusable lessons must state `compoundingDecision: recorded` plus a concrete `reason: ...`.
## Watcher Fallback

For hosts without direct return, missed direct delivery, or recovery audits, use `watch_team_task_with_adapter()` from a real scheduler/automation. The watcher reads the ledger/registry recovery anchor, calls `read_thread`, captures a manager plan, executor callback, reviewer review, or verifier verdict, and immediately performs the next safe parent continuation such as sending executor work, sending reviewer work, sending verifier work, or returning closeout `userOutput`.

It returns `action`, `status`, `userOutput`, `nextWakeup`, `watcher`, and `automationBoundary`. If `nextWakeup` is not null, the host automation must schedule another watcher call for that role/anchor. Direct return is possible when role threads are instructed with `returnThreadId`, `orchestratorThreadId`, `roleThreadId`, `sourceRoleThreadId`, and `role` and can call `send_message_to_thread`; manager inbox capture validates taskId, protocol-block sourceThreadId -> returnThreadId, role, sourceRoleThreadId, expected marker, and the currently awaited role before advancing. Duplicate direct callbacks are ignored after the ledger advances. watcher/scheduler polling is the fallback when direct-send is unavailable or misses delivery, using the normal 5 minutes cadence.

When the verifier returns `needs_rework`, the runner stops with `action: needs_rework_pending`. Call it with `confirm_rework=True` only after the user approves another executor dispatch.

Manager watcher heartbeat contract: ordinary manager watcher/read_thread polling for the same role thread is at most once every 5 minutes (300 seconds). The app or host heartbeat must use the watcher ledger fields role/thread id, expected marker, lastReadAt, firstCheckAt, nextAllowedReadAt, waiting reason, and next manager action to call watch_team_task_with_adapter() at wake time. Run one short observation-only first check at firstCheckAt so very fast role completions can be received immediately; after that single short check, use one short observation-only first check, then stop proactive reads until firstCheckAt or nextAllowedReadAt and return to the normal 5 minutes heartbeat cadence. inProgress is not polling permission; wait for direct-send, user-triggered status/stop/immediate, firstCheckAt, nextAllowedReadAt, known expected completion window, or timeout/blocker handling. User-triggered status/stop/immediate requests may bypass the 300 second wait, but active/running role threads still require observation-only waiting and no convergence instruction. Role writing a marker is not receipt by the manager; self-thread-marker writes only to the role thread and requires explicit result collection read/check; completion feedback is received only when direct-send reaches the manager inbox or the watcher/heartbeat reads the role thread and captures TEAM_ROUTER_PLAN, TEAM_ROUTER_CALLBACK, TEAM_ROUTER_REVIEW, or TEAM_ROUTER_VERDICT. If a role appears completed or idle without the expected marker, the manager records needs_feedback/missing protocol and asks the same role thread for structured feedback instead of treating the task as successful; after bounded wait/read, that CONTROL request must demand scope-limited closeout from already-confirmed facts. When the flow finishes, report the result once in plain language for the user, stop_and_delete_heartbeat for accepted closeout, explicitly say stage/commit/push/PR/publish/release were not done, and keep the manager boundary: the manager/dispatcher does not directly edit files unless the user explicitly authorizes that specific file change; commit/PR/publish/release require a separate prompt and authorization.

Compatibility anchor: legacy shorthand send_message_to_thread(sourceThreadId, protocolBlock) means the same protocol delivery target as send_message_to_thread(threadId=<returnThreadId>, prompt=<完整 TEAM_ROUTER_* block>); prefer the explicit `threadId=<returnThreadId>` form in role request templates.
